Plataforma MCP (Managed Control Plane) — Pesquisa para Construção de Serviço Próprio

Objetivo: Estruturar uma plataforma MCP multi-tenant para oferecer como serviço (B2B), com billing, autenticação/SSO, tokens, isolamento de dados e provisionamento self-service.

1. Visão Geral & Oportunidade

Aspecto Detalhamento
Definição Control Plane gerenciado que provisiona, opera e cobra data planes de identidade (AuthN/AuthZ) por tenant.
Público-alvo SaaS B2B, ISVs, agências digitais, empresas com múltiplos produtos/clientes que precisam de SSO, MFA, SCIM, audit logs sem montar infra própria.
Diferenciais vs. Auth0/Okta Preço previsível (flat + MAU), white-label total, data residency (LGPD), onboarding self-service via API, integração nativa com stack do cliente (n8n, Supabase, etc.).
Modelo de negócio Plataforma (control plane) + Data Planes dedicados ou compartilhados por tier. Receita: subscription base + overage MAU + add-ons (MFA, SCIM, SIEM streaming, custom domains).

Fluxo de Login (Authorization Code Flow + PKCE)

sequenceDiagram
    autonumber
    actor User
    participant App as Aplicação Cliente
    participant Browser
    participant DP as Data Plane (Keycloak)
    participant IdP as Enterprise IdP (SAML/OIDC)
    User->>Browser: Acessa app
    Browser->>App: GET /
    App->>Browser: Redirect → /authorize?client_id&redirect_uri&scope&code_challenge
    Browser->>DP: GET /realms/{tenant}/protocol/openid-connect/auth
    alt First factor
        DP->>Browser: Login page (branding tenant)
        User->>Browser: Credenciais / Social / Passkey
    else Enterprise SSO
        DP->>IdP: Redirect SAML AuthnRequest / OIDC
        IdP->>Browser: Login corporativo
        Browser->>DP: Assertion / Callback
    end
    DP->>DP: Valida, cria sessão, emite code
    DP->>Browser: Redirect → redirect_uri?code=...
    Browser->>App: GET /callback?code=...
    App->>DP: POST /token (code + code_verifier + client_secret)
    DP->>App: {access_token, id_token, refresh_token, expires_in}
    App->>Browser: Set secure HttpOnly cookies / token em memória
    Browser->>App: Requests com Authorization: Bearer <access_token>

Checklist de Conformidade (LGPD / SOC 2 Type II)

  • [ ] Data Processing Addendum (DPA) padrão + sub-processadores listados
  • [ ] Right to be forgotten → API DELETE /tenants/{id}/users/{userId} + purge job 30d
  • [ ] Data Portability → Export JSON/CSV completo via Admin Console ou API
  • [ ] Breach Notification < 72h (processo documentado + templates)
  • [ ] Encryption Keys → AWS KMS / GCP KMS / HashiCorp Vault; rotação 90d
  • [ ] Pen Test anual + bug bounty (HackerOne/Intigriti)
  • [ ] SOC 2 Type II → Auditoria anual (Vanta/Drata para automação)

Minha Recomendação Inicial

Keycloak (Quarkus) + Control Plane próprio em Go/TypeScript - Realms = isolamento nativo testado em produção massiva - SPIs para customização (custom authenticators, event listeners, user storage) - Admin API completa para provisionamento automatizado - Comunidade grande, suporte comercial (Red Hat, Skycloak, Inteca) - Roadmap: migrar data planes para SuperTokens Core no tier Starter (menor footprint) mantendo Keycloak no Enterprise/BYOC
